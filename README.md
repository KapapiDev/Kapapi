# KAPAPI

> **WORK IS A QUEST.**  
> **DROP WORK. GET RESULTS.**

## 전문가를 찾지 마세요. 결과를 주문하세요.

KAPAPI는 필요한 온라인 전문업무를 맡길 때 사람이 직접 전문가를 찾고, 포트폴리오를 비교하고, 견적과 일정을 협의하고, 계약하고, 업무를 설명하고, 진행상황을 관리해야 했던 기존 외주 과정을 줄여 나가는 **결과 중심 전문업무 플랫폼**입니다.

초기 KAPAPI는 **온라인 전문업무가 필요한 사람이 업무를 등록하면, 전문가들이 가격과 완료시간을 함께 제안하고, 의뢰자가 원하는 조건의 전문가를 선택하는 마켓플레이스**로 시작합니다.

```text
업무 등록
   ↓
전문가들이 가격 + 완료시간 제안
   ↓
가격 / 납기 / 경력 / 신뢰도 비교
   ↓
전문가 선택
   ↓
작업 / 납품 / 검수
```

KAPAPI는 이 거래 과정을 기억하기 쉽고 재미있게 표현하기 위해 하나의 가벼운 세계관을 사용합니다.

- 업무를 의뢰하는 사람 = **GM**
- 업무를 수행하는 전문가 = **PLAYER**
- 등록된 업무 = **QUEST**
- 가격 + 완료시간 제안 = **BID**
- 긴급 업무 = **TIME ATTACK**

따라서 KAPAPI식으로 표현하면 초기 거래 구조는 다음과 같습니다.

> **GM이 QUEST 등록 → PLAYER들이 PRICE + DELIVERY TIME으로 BID → GM이 선택 → 결과물 납품**

세계관은 제품을 기억하기 쉽게 만드는 표현 방식일 뿐, 거래 자체는 전문적인 외주 거래입니다. 계약, 결제, 보안, NDA, 납품, 증빙과 분쟁 영역은 게임처럼 가볍게 다루지 않습니다.

장기적으로는 이 초기 마켓플레이스보다 한 단계 더 나아갑니다.

GM이 파일과 짧은 지시, 원하는 결과와 기한만 전달하면 KAPAPI가 업무 정의, 적합한 전문가 탐색과 선정, 입찰 또는 배정, 계약과 보안, 진행관리, 필요 시 대체 인력 투입까지 오케스트레이션하고 **완성된 결과물을 전달하는 Autopilot형 전문업무 처리 시스템**을 지향합니다.

```text
기존 외주 플랫폼
사람 찾기 → 포트폴리오 → 문의 → 견적 → 일정 → 계약 → 설명 → 관리 → 수정 → 결과

KAPAPI의 최종 방향
업무 투입 → KAPAPI → 결과
```

KAPAPI가 만들고 싶은 것은 더 좋은 프리랜서 검색창이 아닙니다.

> **사람을 찾을 필요 자체를 점점 없애는 외주 플랫폼입니다.**

## 1. 우리가 해결하려는 문제

작은 조직과 전문가는 항상 일정한 양의 업무만 처리하지 않습니다.

평소에는 내부 인력으로 충분하지만 여러 프로젝트가 겹치거나 갑자기 새로운 업무가 발생하면 짧은 기간 동안 조직의 처리능력을 넘어서는 순간이 생깁니다.

KAPAPI가 현재 보는 대표적인 수요 발생 원인은 네 가지입니다.

### Capacity Gap

업무를 할 능력은 있지만 **지금 처리할 시간이 부족한 상황**입니다.

### Skill Gap

조직 내부에 **해당 업무에 필요한 특정 기술이 없는 상황**입니다.

### Deadline Gap

직접 할 수는 있지만 **요구된 마감시간 안에는 끝낼 수 없는 상황**입니다.

### Employment Gap

업무가 계속 발생하는 것은 아니어서 **정규 인력을 채용하기에는 불규칙하거나 작은 상황**입니다.

따라서 KAPAPI의 초기 핵심 의뢰자를 단순히 “1인 사업자”라고 정의하지 않습니다.

> **지금 당장 자기 조직의 처리능력을 넘어선 작은 전문업무가 발생한 사람 또는 조직**

이 더 정확한 정의입니다.

초기 가설상 다음과 같은 조직이 주요 고객 후보입니다.

- 1~10인 규모의 전문서비스 회사
- 1인 사업자와 독립 전문직
- 소규모 건축·인테리어·디자인 사무소
- 마케팅·콘텐츠·제작 에이전시
- 소규모 쇼핑몰·커머스 팀
- 크리에이터 팀
- 작은 스타트업과 개발팀

KAPAPI 세계관에서는 이 업무 의뢰자를 **GM**이라고 부릅니다.

## 2. 가장 중요한 제품 인사이트

처음에는 이런 질문에서 시작했습니다.

> “어떻게 GM이 좋은 PLAYER를 더 빨리 찾게 만들 것인가?”

하지만 실제 외주 행동을 파고들면서 질문이 바뀌었습니다.

> **GM은 사실 PLAYER를 찾고 싶은 것이 아니다. 원하는 시간 안에 원하는 품질의 결과물을 받고 싶은 것이다.**

누가 작업하는지, 어떤 방식으로 입찰하는지, 계약을 어떻게 처리하는지는 GM에게 본질적인 목적이 아닙니다.

그 모든 과정은 결과를 받기 위한 수단입니다.

따라서 KAPAPI의 장기 제품 질문은 항상 이것입니다.

> **이 단계를 GM의 업무에서 없앨 수 있는가?**

- 전문가 검색을 없앨 수 있는가?
- 업무 설명을 줄일 수 있는가?
- 견적 비교를 자동화할 수 있는가?
- 가용성 확인을 자동화할 수 있는가?
- 계약과 NDA를 자동화할 수 있는가?
- 진행상황을 GM이 일일이 확인하지 않아도 되는가?
- PLAYER가 실패했을 때 GM이 다시 사람을 찾지 않아도 되는가?

궁극적으로 목표는 다음 두 점 사이의 거리를 최소화하는 것입니다.

```text
업무 발생  ───────────────────────>  원하는 결과 수령
```

## 3. 핵심 거래 메커니즘: PRICE × DELIVERY TIME

초기 KAPAPI에서는 업무가 필요한 사람이 QUEST를 등록하고, PLAYER들이 BID를 제출합니다.

모든 BID에는 반드시 두 가지가 함께 포함됩니다.

1. **PRICE** — 얼마에 수행할 것인가
2. **DELIVERY TIME** — 계약 성립 후 얼마 안에 결과물을 제출할 것인가

예시:

| PLAYER | PRICE | DELIVERY TIME |
| --- | ---: | ---: |
| A | 100,000원 | 18시간 |
| B | 150,000원 | 8시간 |
| C | 220,000원 | 4시간 |

DELIVERY TIME은 예상 노동시간이 아닙니다.

> **GM이 PLAYER를 선택한 시점부터 결과물이 제출될 때까지의 약속된 실제 경과시간**입니다.

KAPAPI는 최저가 낙찰 플랫폼을 지향하지 않습니다.

GM은 상황에 따라 가격보다 다음 요소를 더 중요하게 볼 수 있습니다.

- 해당 분야 실무경력
- 같은 종류의 QUEST 완료이력
- 납기 준수율
- 수정·재작업률
- 평가
- 현재 가용성
- 완료속도
- 가격

특히 긴급한 상황에서는 가격보다 **“제시간에 제대로 나온다”는 신뢰**가 더 높은 가치를 가질 수 있습니다.

이 긴급 QUEST를 KAPAPI에서는 **TIME ATTACK**이라고 부릅니다.

## 4. KAPAPI 세계관

KAPAPI는 외주라는 다소 건조한 경험에 가벼운 게임 세계관을 입힙니다.

| KAPAPI 용어 | 일반적인 의미 |
| --- | --- |
| **GM** | 발주자 / 의뢰자 / QUEST 생성자 |
| **PLAYER** | 독립적으로 업무를 수행하는 전문가 |
| **QUEST** | 하나의 명확한 전문업무 단위 |
| **BID** | 가격 + 완료시간 제안 |
| **REWARD** | 업무 보상 |
| **TIME ATTACK** | 긴급발주 QUEST |
| **LEVEL / EXP** | 신뢰·실적·수행이력 |
| **QUEST COMPLETE** | 업무 완료 상태 |

세계관의 원칙은 단순합니다.

> **겉은 게임처럼 재미있게, 속은 Upwork보다 진지하게.**

탐색, 성장, 완료 경험에는 게임적 언어를 사용할 수 있지만 다음 영역은 철저하게 전문 서비스처럼 보여야 합니다.

- 계약
- 결제
- NDA
- 개인정보 및 파일보안
- 납품
- 분쟁
- 증빙

게임화가 B2B 신뢰를 훼손해서는 안 됩니다.

또한 GM과 PLAYER는 영구적인 계정 계급이 아닙니다. 한 사용자가 어떤 업무에서는 GM일 수 있고, 다른 업무에서는 PLAYER일 수 있습니다.

## 5. 제품은 세 단계로 진화합니다

### Stage A — Marketplace Mode

첫 단계는 실제 시장을 만드는 것입니다.

```text
GM
 ↓
QUEST 등록
 ↓
PLAYER BID
PRICE + DELIVERY TIME
 ↓
GM 비교 / 선택
 ↓
작업
 ↓
납품 / 검수
 ↓
QUEST COMPLETE
```

이 단계의 목적은 단순 기능 구현이 아닙니다.

- 실제 GM 수요가 있는지 검증
- 어떤 업무가 거래되기 좋은지 확인
- PLAYER 공급과 유동성 확보
- 가격과 납기 데이터 축적
- 신뢰지표 구축
- 실제 실패·수정 패턴 학습

Marketplace는 **KAPAPI Autopilot을 만들기 위한 시장과 데이터의 시작점**입니다.

### Stage B — Assist Mode

다음 단계에서는 GM이 QUEST를 직접 정교하게 작성할 필요도 줄입니다.

```text
파일 업로드 + 짧은 지시
        ↓
AI가 업무 분석
        ↓
QUEST / 업무지시서 자동 생성
        ↓
필요 정보 확인
        ↓
적합 PLAYER 추천
        ↓
GM 승인
        ↓
작업 / 결과
```

예를 들어 GM은 이렇게만 입력할 수 있습니다.

> “이 현황도 자료 CAD로 따주세요. 내일 오후 3시까지.”

KAPAPI는 파일과 문장을 바탕으로 다음을 구조화합니다.

- 업무범위
- 입력자료
- 필요한 결과물
- 파일형식
- 납기
- 누락된 정보
- 필요한 보안조건
- 적합한 PLAYER 후보
- 시장의 참고 가격·납기 범위

AI는 최종 가격 결정자나 주관적 품질 심판이 아니라 **외주를 맡기기 위해 필요한 설명과 관리 부담을 줄이는 도구**로 먼저 사용합니다.

### Stage C — Autopilot Mode

KAPAPI의 장기 North Star입니다.

```text
GM
“이거 내일 18시까지 끝내줘.”
+ 파일

        ↓

KAPAPI
업무 정의
PLAYER 선택 / 입찰
계약 / NDA
작업 배정
진행 추적
위험 감지
필요 시 PLAYER 교체
기본 사전검수

        ↓

GM
완성된 결과물 검수
```

이 단계에서는 GM이 PLAYER를 직접 고르는 것조차 선택사항이 될 수 있습니다.

GM이 원하는 것은 입찰 과정을 구경하는 것이 아니라 **정해진 시간에 사용할 수 있는 결과물이 도착하는 것**이기 때문입니다.

Autopilot은 현재 제공 기능이 아니라 **장기 제품 비전**입니다.

충분한 거래 데이터, 공급 유동성, 품질관리 능력, 대체 PLAYER 운영능력과 실제 성공률이 확보된 좁은 업무군부터 검증해야 합니다.

## 6. 기존 외주 플랫폼과의 차이

기존 프리랜서·외주 플랫폼의 중심 객체는 대체로 **사람 또는 서비스 상품**입니다.

사용자가 사람을 찾고 판단하고 관리해야 합니다.

KAPAPI가 궁극적으로 중심에 두려는 객체는 **결과물**입니다.

```text
기존 방식
내가 적합한 사람을 찾아서 일을 맡긴다.

KAPAPI
내가 원하는 결과를 요청하면 필요한 사람이 뒤에서 연결된다.
```

초기 Marketplace 단계에서는 기존 외주 플랫폼과 겹치는 부분이 있습니다.

하지만 KAPAPI가 발전할수록 다음 과정이 점점 플랫폼 내부로 내려갑니다.

- 사람 찾기
- 실력 판단
- 가용성 확인
- 가격 비교
- 납기 비교
- 업무지시서 작성
- 계약
- NDA
- 증빙
- 진행관리
- 실패 시 대체인력 탐색

따라서 KAPAPI의 최종 경쟁대상은 단순히 다른 프리랜서 플랫폼만이 아닙니다.

많은 GM이 현재 선택하는 가장 강력한 대안은:

> **“그냥 내가 야근해서 하지.”**

입니다.

KAPAPI가 성공하려면 외주를 맡기는 전체 거래비용을 GM이 직접 처리하는 비용보다 낮춰야 합니다.

## 7. 초기 Wedge: 건축 / CAD

KAPAPI가 처음부터 모든 전문업무를 다루지는 않습니다.

초기 검증용 Wedge는 **건축/CAD 관련 명확한 제작업무**입니다.

이 분야를 선택한 이유는 다음과 같습니다.

- 실제 업무 흐름을 이해할 수 있음
- 현실적인 QUEST를 만들 수 있음
- 결과물의 품질을 판단할 수 있음
- 작은 사무소에서 Capacity Gap과 Deadline Gap이 실제로 발생함
- 파일 기반 디지털 업무가 존재함

대표적인 초기 QUEST 예시:

> 제공된 손도면 또는 현황자료를 기준으로 지정된 형식의 DWG 현황도를 작성하여 정해진 기한까지 납품한다.

이 업무는 “직원이 하기 아까운 잡일”이 아닙니다.

실제 건축 프로젝트의 정상적인 업무이지만 여러 프로젝트가 동시에 겹치거나 인력이 부족한 순간 **병목이 되는 프로젝트 업무**입니다.

건축/CAD는 KAPAPI 전체 시장이 아닙니다.

> **첫 번째 실험실일 뿐입니다.**

검증 후에는 결과가 명확하고 디지털 전달이 가능한 다른 전문업무로 확장할 수 있습니다.

예시 후보:

- 렌더링
- 이미지 편집
- PPT 정리
- Excel / 데이터 정리
- 쇼핑몰 상품등록
- 간단한 웹 수정
- 간단한 코드 수정
- 번역 / 교정
- 영상 자막 / 컷 편집

## 8. 어떤 업무가 KAPAPI에 잘 맞는가

초기에는 다음 조건을 만족하는 업무를 우선합니다.

- 온라인으로 자료 전달 가능
- 결과물이 명확함
- 몇 시간 ~ 약 2일 정도에 완료 가능
- GM이 결과를 검수할 수 있음
- 요구사항을 어느 정도 표준화할 수 있음
- 오류가 발생해도 수정 가능
- 법적·안전상 높은 책임이 없는 업무

반대로 초기에는 다음 업무를 지양합니다.

- 매우 긴 대형 프로젝트
- 광범위한 전략 컨설팅
- 주관성이 지나치게 높은 전체 브랜딩
- 고위험 전문 판단
- 법적으로 자격이 요구되는 업무의 무자격 수행
- 실패를 되돌리기 어려운 고책임 업무

---

## 9. 신뢰는 단순 별점보다 깊어야 합니다

전문업무에서는 “평점 4.9”만으로 부족합니다.

GM이 실제로 궁금한 것은:

> **“이 사람에게 자료만 넘겨도 내가 설명을 거의 안 하고 원하는 결과가 나올까?”**

입니다.

따라서 PLAYER 프로필은 장기적으로 다음 신호를 중요하게 다뤄야 합니다.

- 본인확인
- 실제 관련 경력
- 동일한 QUEST 유형 수행이력
- 완료건수
- 납기 준수율
- 수정률
- 평가
- 허용된 범위의 포트폴리오

예를 들어 건축 CAD 업무에서:

> **건축사사무소 경력 5년**

이라는 정보는 단순 스펙이 아닙니다.

GM에게는:

> “건축 실무를 이해하니 자료만 넘겨도 설명비용이 적겠다.”

라는 신호가 됩니다.

즉 KAPAPI에서 신뢰는 **업무 설명비용을 줄이는 장치**이기도 합니다.

---

## 10. 보안·계약·행정도 제품의 일부입니다

전문업무 외주에서 마찰은 사람 찾기에만 존재하지 않습니다.

GM은 다음도 신경 써야 합니다.

- 프로젝트 파일 유출
- NDA
- 외부 제공 금지
- 포트폴리오 무단사용
- 계약
- 납품 증빙
- 거래 기록
- 결제
- 세금·증빙
- 분쟁

KAPAPI는 장기적으로 이 행정비용까지 줄이는 것을 목표로 합니다.

특히 기밀성이 있는 업무는 다음을 지원하는 방향을 검토합니다.

- QUEST별 NDA
- 제3자 제공 금지
- GM 동의 없는 포트폴리오 사용 금지
- 작업 후 데이터 삭제·보관정책
- 계약 및 납품 기록
- 분쟁 증빙

구체적인 법적 구조는 `docs/LEGAL.md`에서 관리합니다.

---

## 11. 기존 거래처도 KAPAPI 안으로 들어올 수 있습니다

현실의 회사는 이미 사용하는 외주업체가 있을 수 있습니다.

KAPAPI는 이 관계를 없애려 하지 않습니다.

오히려 장기적으로 다음 구조를 지향할 수 있습니다.

```text
새 QUEST
  ├─ 기존 파트너 A에게 요청
  ├─ 기존 파트너 B에게 요청
  └─ KAPAPI 신규 PLAYER 시장 공개

            ↓

가격 / 납기 / 경력 / 퀄리티 / 가용성 비교

            ↓

GM 선택
```

가능한 기능:

- 자주 쓰는 외주 파트너 저장
- 기존 파트너의 현재 가용성 확인
- 최근 가격·납기 이력 비교
- 신규 PLAYER와 한 화면에서 비교
- 기존 파트너가 불가능할 때 대체 PLAYER 추천
- 모든 외주업무와 업체 이력 관리

이렇게 되면 KAPAPI는 단순한 신규 프리랜서 발견 사이트를 넘어 **외부 인력과 외주업무를 관리하는 운영 레이어**가 될 수 있습니다.

---

## 12. 탈중개는 실제 위험입니다

좋은 PLAYER를 발견한 GM은 이후 직접 거래할 수 있습니다.

KAPAPI는 이 문제를 인위적인 락인만으로 해결하려 하지 않습니다.

GM이 계속 KAPAPI를 사용할 이유를 만들어야 합니다.

그 이유는 다음과 같을 수 있습니다.

- 계약 자동화
- NDA 자동화
- 거래·납품 증빙
- 결제·정산 편의
- 외주 이력 관리
- 가격 비교
- 새 공급자 발견
- 기존 파트너의 백업
- 가용성 확인
- 분쟁지원
- 향후 결과·납기 보증

장기적으로 GM이 특정 PLAYER가 아니라 **KAPAPI의 결과 전달 능력**을 신뢰하게 된다면 탈중개 문제의 성격 자체가 달라질 수 있습니다.

## 13. 데이터가 쌓이면 무엇이 달라지는가

KAPAPI의 장기적인 자산 후보는 단순 회원 수가 아닙니다.

거래가 쌓이면 다음과 같은 데이터가 축적될 수 있습니다.

- 어떤 QUEST에 어떤 PLAYER가 잘 맞는지
- 업무별 실제 거래가격
- 업무별 실제 완료시간
- PLAYER별 분야 경험
- 납기 성공률
- 수정률
- 작업 실패 패턴
- 대체 PLAYER 투입 성공률
- GM별 선호도
- 분야별 유동성

예를 들어 장기적으로는 다음과 같은 정보를 가질 수 있습니다.

```text
PLAYER C
건축사사무소 경력 5년
현황도 CAD QUEST 142건 완료
평균 완료 5.8시간
24시간 이내 납기 성공률 99%
수정률 3%
```

이런 데이터가 충분히 쌓이면 KAPAPI는 단순 추천을 넘어 **자동 라우팅과 결과 예측**으로 발전할 수 있습니다.

잠재적 플라이휠:

```text
거래 증가
  ↓
업무·PLAYER 데이터 증가
  ↓
더 정확한 업무 정의와 라우팅
  ↓
납기·품질 신뢰도 증가
  ↓
GM이 더 많은 업무를 맡김
  ↓
거래 증가
```

## 14. 현재 검증에서 나온 초기 인사이트

현재까지의 GM 인터뷰는 **시장 검증 완료를 의미하지 않습니다.**

초기 가설을 만드는 질적 근거입니다.

### 실제 문제

여러 프로젝트가 겹치면 직접 할 수 있는 CAD 업무도 시간이 부족해지고 결국 야근·밤샘으로 처리하게 됩니다.

### 외주를 막는 큰 마찰

업무가 쉬워도:

> “설명하는 게 더 귀찮다.”

는 이유로 직접 처리할 수 있습니다.

따라서 AI QUEST 생성과 업무지시서 자동화는 단순 편의기능이 아니라 **외주 자체의 진입비용을 낮추는 핵심 기능 후보**입니다.

### 긴급 상황에서 가격은 절대 1순위가 아닐 수 있음

가상의 입찰에서 더 빠르고 이력이 많은 PLAYER가 최저가보다 2배 이상 비쌌음에도 선택되었습니다.

이유는:

- 더 높은 신뢰
- 빠른 납기
- 많은 완료경험
- 저녁에 결과를 검수하고 퇴근할 수 있음

이었습니다.

이는 `PRICE × DELIVERY TIME`이 단순 가격경쟁보다 풍부한 선택을 만들 가능성을 보여줍니다.

### 좋은 외주업체는 장기 파트너가 될 수 있음

실제 회사 사례에서 단기 외주로 시작한 CG 작업자가 신뢰를 쌓으며 사업자로 확장했고 약 10년간 거래가 이어졌습니다.

이후 더 높은 품질의 신규 업체가 발견되면서:

- 기존 업체는 급하거나 간단한 업무
- 신규 업체는 높은 퀄리티가 필요한 업무

로 외주 네트워크가 분화되었습니다.

즉 GM은 한 명의 PLAYER만 영구 선택하기보다 **자신만의 외주 공급망을 만들어갈 수 있습니다.**

KAPAPI는 그 공급망을 발견하고 확장하며 관리하는 도구가 될 가능성이 있습니다.

보다 상세한 검증 기록은 `docs/VALIDATION.md`에 정리합니다.

## 15. 현재 단계

현재 KAPAPI는 **제품 설계 및 초기 검증 단계**입니다.

2026년 `모두의 창업 프로젝트` 일반·기술 트랙 1R 지원을 첫 외부 검증 계기로 활용하는 방향을 준비하고 있습니다.

현재 목표는 완성형 상용 플랫폼을 미리 만드는 것이 아닙니다.

1R 이전에는 핵심 메커니즘을 명확하게 보여줄 수 있는 **얇지만 높은 완성도의 프로토타입**을 만드는 것이 우선입니다.

### 1R 프로토타입 핵심 범위

- 일반어로 이해 가능한 서비스 소개와 GM/PLAYER 진입
- QUEST 생성
- QUEST 목록
- PLAYER의 PRICE + DELIVERY TIME BID
- GM의 BID 비교
- PLAYER 선택
- TIME ATTACK 표현
- PLAYER 경력 / LEVEL / EXP
- 작업 진행 / 완료 흐름
- NDA·보안 개념 표현
- 실제 건축/CAD 예시 QUEST

### 지금 만들지 않는 것

- 실제 PG/에스크로
- 복잡한 세금 자동화
- 정교한 분쟁센터
- 네이티브 모바일 앱
- 광범위한 전체 카테고리
- 완전한 Autopilot 결과보증
- AI의 주관적 품질 최종판정

프로토타입의 목적은:

> **“그래서 이 서비스가 실제로 어떻게 작동하는데?”**

라는 질문을 없애는 것입니다.

## 17. 법적 제품 경계

KAPAPI는 현재 **결과물 기반 독립 용역 거래**를 기본 구조로 설계합니다.

PLAYER의 근무시간이나 장소를 통제하는 단기 고용·근로자 파견 서비스가 아닙니다.

기본 원칙:

- GM은 원하는 결과와 납기를 정의
- PLAYER는 자신의 가격과 완료시간을 제안
- PLAYER가 작업시간·장소·방식을 독립적으로 결정
- KAPAPI는 거래·매칭·오케스트레이션을 지원

초기에는 법적 자격이 필요한 전문 판단 업무를 함부로 거래 대상으로 열지 않습니다.

건축 분야에서도 CAD 작성 보조·자료 디지털화 등과 법적으로 건축사의 역할이 요구되는 설계업무를 구분해야 합니다.

결제·에스크로, 세금, 저작권, 개인정보, 파일보안, Autopilot의 책임범위 등 상세 원칙은 `docs/LEGAL.md`에 별도로 관리합니다.

## 18. 현재 핵심 가설과 리스크

KAPAPI는 아직 시장 검증 전 단계이므로 아래 문제들은 해결됐다고 가정하지 않습니다.

- GM 수요가 충분히 자주 발생하는가
- 모르는 PLAYER에게 실제 업무파일을 맡길 만큼 신뢰할 수 있는가
- 업무 설명비용을 충분히 줄일 수 있는가
- PRICE + DELIVERY TIME 입찰이 실제 선택가치를 만드는가
- 카테고리별 충분한 PLAYER 유동성을 확보할 수 있는가
- TIME ATTACK을 성립시킬 만큼 실시간 공급이 존재하는가
- 좋은 GM·PLAYER가 직접거래로 이탈하는 문제를 어떻게 해결할 것인가
- 결과 품질 분쟁의 운영비용을 감당할 수 있는가
- Autopilot에서 PLAYER 실패 시 KAPAPI가 결과를 복구할 수 있는가
- 결과보증 수준이 높아질수록 커지는 법적·경제적 책임을 감당할 수 있는가

따라서 현재의 최우선 사업 질문은 회원 수가 아닙니다.

> **실제 GM이 실제 업무를 올리고 실제 돈을 지불할 것인가?**

## 21. Product Principles

KAPAPI를 발전시킬 때 다음 원칙을 우선합니다.

1. **GM이 원하는 것은 PLAYER가 아니라 결과다.**
2. **업무를 맡기는 과정 자체를 줄인다.**
3. **가격만이 아니라 납기와 신뢰를 함께 시장화한다.**
4. **검증된 기존 외주관계를 적으로 만들지 않는다.**
5. **AI는 설명과 운영마찰을 줄이는 데 먼저 사용한다.**
6. **Autopilot은 충분한 데이터와 신뢰성이 생긴 뒤 좁은 영역부터 시작한다.**

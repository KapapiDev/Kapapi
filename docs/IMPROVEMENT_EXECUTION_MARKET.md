# KAPAPI 개선안 — 실시간 업무 실행 시장

Status: **alternative concept / not canonical**  
Branch: `개선안`  
Updated: 2026-09-03

> 이 문서는 기존 KAPAPI의 정본 설계를 대체하지 않는다.  
> 기존 `feat/prototype-v2`의 **Task Marketplace → Recommendation → Routing → Outcome Layer** 경로와 분리하여, 처음부터 사용자에게 사람 선택을 요구하지 않는 구조가 더 강한 제품이 될 수 있는지 검토하기 위한 대안 설계다.

---

## 1. 한 줄 정의

> **작은 디지털 업무를 입력하면 가격과 완료시각이 나오고, 결제하면 KAPAPI가 사람·AI·자동화를 알아서 조달·교체하여 결과만 반환하는 업무 실행 시장.**

North Star:

> **해야 할 일을 넣으면, 결과가 나온다.**

핵심 변화는 단순하다.

기존 KAPAPI가 사용자의 **작업자 선택 비용을 줄이는 것**이라면, 이 개선안은 **작업자 선택 자체를 사용자 경험에서 제거한다.**

사용자는 프리랜서를 고용하지 않는다.

사용자는 **완료된 업무를 구매한다.**

---

## 2. 이 개선안이 필요한 이유

기존 KAPAPI의 초기 구조는 다음과 같다.

```text
GM이 QUEST 등록
→ PLAYER들이 PRICE + DELIVERY 제안
→ KAPAPI가 추천
→ GM이 작업자 확인/선택
→ 실행
→ 결과
```

이 구조는 task-first, PRICE × DELIVERY, 추천이라는 차이가 있지만 여전히 본질적으로는 **프리랜서/외주 마켓플레이스의 한 변형**으로 보일 수 있다.

사용자는 여전히 다음 질문을 해야 한다.

- 누구에게 맡길까?
- 이 작업자는 믿을 만한가?
- 더 싼 제안이 나은가?
- 빠른 사람이 나은가?
- 실패하면 다시 누구를 찾지?

이 개선안은 그 질문을 KAPAPI 내부로 이동시킨다.

사용자가 보는 질문은 두 개만 남긴다.

1. **얼마인가?**
2. **언제 끝나는가?**

그리고 가능하면 최종적으로는 하나만 남긴다.

> **이 조건으로 맡길 것인가?**

---

## 3. 제품의 기본 경험

### GM 경험

```text
해야 할 일 입력 / 파일 첨부
→ KAPAPI가 범위 구조화
→ 가격 + 완료예정시각 제시
→ GM 결제/승인
→ KAPAPI 내부 실행
→ 결과 전달
→ 승인 또는 수정 요청
```

예시:

```text
PDF 30개의 표 데이터를 엑셀 한 파일로 정리해주세요.
[파일 30개 첨부]

KAPAPI
예상 결과: 정리된 XLSX 1개
가격: 49,000원
완료 예정: 오늘 19:30
수정: 범위 내 1회 포함

[이 조건으로 맡기기]
```

GM에게 기본적으로 보여주지 않는 것:

- PLAYER 목록
- 공개 BID 목록
- 여러 작업자 프로필 비교
- 작업자 검색
- 협상 과정
- 내부적으로 사람이 하는지 AI가 하는지에 대한 불필요한 실행 세부사항

단, 법률·보안·자격·개인정보 또는 계약상 공개가 필요한 경우 필요한 범위에서는 실행 주체와 조건을 명시해야 한다.

---

## 4. 무엇을 파는가

기존 외주 마켓의 대표 상품은 대체로 다음 중 하나다.

```text
사람
서비스 패키지
전문가와의 계약 기회
```

개선안 KAPAPI의 상품은:

```text
정의된 결과 + 가격 + 완료시각
```

따라서 GM의 구매 단위는 PLAYER가 아니라 **Execution Contract**다.

Execution Contract 최소 구성:

- 입력 자료
- 작업 범위
- 결과물
- 결과 형식
- 가격
- 완료 예정시각
- 객관적 검수 조건
- 수정 범위
- 보안/기밀 조건
- 취소/실패/환불 조건

즉 KAPAPI는 단순 중개 화면이 아니라 **업무를 실행 가능한 계약 단위로 바꾸는 시스템**이 된다.

---

## 5. 내부에는 시장이 남는다

사용자에게 마켓을 숨긴다고 해서 시장 메커니즘을 없애는 것은 아니다.

오히려 기존 KAPAPI의 **PRICE × DELIVERY**는 이 구조에서 더 명확한 존재 이유를 갖는다.

예:

```text
GM에게 제시된 실행 계약
49,000원 / 오늘 19:30

KAPAPI 내부 공급
PLAYER A: 27,000원 / 6H
PLAYER B: 31,000원 / 3H
PLAYER C: 42,000원 / 1.5H
AI workflow: 8,000원 상당 / 즉시 초안 + human QA 필요
Automation: 특정 형식이면 자동 처리 가능
```

KAPAPI는 내부적으로 다음을 판단한다.

- 누가 이 TASK를 수행할 자격이 있는가
- 실제 가용한가
- 어느 가격에 수락 가능한가
- 어느 시간 안에 끝낼 확률이 높은가
- 수정 가능성이 얼마나 되는가
- 실패 시 대체 가능한 공급이 있는가
- AI/자동화로 일부를 줄일 수 있는가
- 한 명이 아닌 여러 실행 단위로 분해하는 편이 나은가

따라서 PRICE × DELIVERY는 **마케팅용 입찰 UI**가 아니라 **실행 자원을 가격 발견하고 조달하기 위한 내부 시장 신호**가 된다.

---

## 6. 공급자 경험도 달라진다

PLAYER에게도 반드시 공개 게시판을 탐색하게 할 필요는 없다.

### 모델 A — 내부 BID

```text
KAPAPI가 적합한 PLAYER에게 QUEST 노출
→ PLAYER가 PRICE + DELIVERY 제출
→ 내부 엔진이 실행자 선택
```

### 모델 B — 자동 Offer

PLAYER가 미리 등록:

- 가능한 업무 유형
- 검증된 스킬
- 희망 단가 범위
- 최소 보상
- 현재 가용시간
- 최대 동시 작업량
- 긴급작업 수락 여부

KAPAPI:

```text
업무 도착
→ 적합한 PLAYER에게 38,000원 / 3시간 조건 제시
→ PLAYER 수락
→ 실행
```

### 모델 C — 혼합

일반 작업은 Offer, 희소하거나 불확실한 작업은 BID로 가격을 발견한다.

장기적으로 GM에게 마켓을 숨기더라도 PLAYER 측에는 **실시간 노동 공급 시장**이 존재할 수 있다.

---

## 7. 실행 자원은 사람에 한정하지 않는다

KAPAPI가 판매하는 것이 사람이 아니라 결과라면, 내부 실행 방식은 자원 중립적일 수 있다.

가능한 실행 자원:

- human PLAYER
- AI model / agent
- deterministic automation
- 전문 파트너
- human + AI hybrid
- 여러 PLAYER의 분업

예:

```text
PDF 자료 100개 요약

1. OCR/구조화: automation
2. 초안 추출: AI
3. 오류 확인: PLAYER
4. 최종 병합: automation
5. 결과 검수: KAPAPI preflight
```

GM은 내부 파이프라인을 설계할 필요가 없다.

그 책임이 KAPAPI로 이동한다.

---

## 8. KAPAPI가 실제로 책임져야 하는 것

이 모델에서 가장 중요한 차별점은 **추천 정확도**가 아니다.

> **실행이 실패했을 때 사용자에게 다시 공급자 탐색을 떠넘기지 않는 것.**

### Recovery loop

```text
TASK assigned
→ 진행 상태 감시
→ 지연/실패 위험 감지
→ 필요 시 백업 실행자 확보
→ 재배정 또는 병렬 복구
→ 결과 제출
```

예:

```text
19:30 완료 약속
↓
PLAYER A가 중도 이탈
↓
GM에게 "새 사람을 고르세요"라고 하지 않음
↓
KAPAPI가 PLAYER B 또는 다른 실행 방식으로 복구
↓
가능한 한 기존 계약 조건 안에서 결과를 완성
```

이때부터 KAPAPI의 핵심 데이터는 단순 별점이 아니다.

- task type
- scope shape
- accepted PRICE
- committed DELIVERY
- actual completion time
- revision count
- failure cause
- replacement success
- recovery cost
- GM acceptance

이 데이터가 누적되면 KAPAPI는 **어떤 실행 자원 조합이 어떤 업무를 실제로 끝내는가**를 학습할 수 있다.

## 9. 기존 KAPAPI와 구조 비교

| 구분 | 기존 KAPAPI v2 | 개선안 |
| --- | --- | --- |
| 핵심 객체 | QUEST | Execution Contract / 결과 |
| GM의 행동 | 등록 → 추천 확인 → PLAYER 선택 | 입력 → 가격/완료시각 확인 → 맡기기 |
| PLAYER 노출 | 기본적으로 보임 | 기본적으로 내부 공급자로 숨김 |
| BID | GM 의사결정에도 사용 | 내부 가격발견/조달에 사용 |
| 프로필 비교 | 존재 | 기본 UX에서 제거 |
| KAPAPI 역할 | 시장 + 추천자 | 실행 계약자/오케스트레이터에 가까움 |
| 실패 시 | 추천/재배정으로 발전 | 복구가 핵심 제품 책임 |
| 결과 책임 | 점진적으로 확대 | 처음부터 제품 중심에 둠 |
| AI/자동화 | 장기 확장 자원 | 초기부터 가능한 내부 실행 자원 |
| 사용자 mental model | 좋은 작업자를 찾기 쉽게 | 그냥 일을 맡기기 |

## 10. 이것은 "한국형 Upwork"가 아니다

이 개선안을 **한국형 Upwork**로 정의하면 제품의 핵심이 다시 사람 매칭으로 돌아간다.

KAPAPI가 지향하는 사용자 mental model은:

```text
누구를 고를까?    X
누구에게 외주줄까? X

이 일 얼마면 언제 끝나지? O
이 조건이면 맡길까?        O
```

비유적으로는 talent marketplace보다 **work execution infrastructure**에 가깝다.

사용자는 클라우드 서버를 이용할 때 데이터센터 안에서 어떤 엔지니어가 서버를 관리할지 고르지 않는다.

개선안 KAPAPI도 작은 디지털 업무에서 실행 자원 선택을 내부화하는 것을 목표로 한다.

다만 이 비유는 제품 방향을 설명하기 위한 것이며, KAPAPI가 실제로 클라우드와 동일한 경제구조나 자동화 수준을 가진다는 의미는 아니다.

## 11. 초기 적용 업무

모든 업무를 즉시 fixed-price / fixed-delivery로 받는 것은 위험하다.

초기에는 다음 특성을 가진 작업만 Execution Contract로 다룬다.

- 디지털 입력/출력
- 범위가 명확함
- 결과물을 눈으로 확인 가능
- 작업 시간이 수십 분~1일 수준
- 객관적 체크 항목을 만들 수 있음
- 수정으로 복구 가능
- 전문직 법정 판단이나 고위험 책임이 없음
- 유사 업무 반복성이 높음
- 대체 가능한 공급자가 여러 명 존재할 가능성이 높음

좋은 초기 후보:

- PDF/문서 → 스프레드시트 정리
- 엑셀 데이터 정리/병합
- 문서/보고서 서식 통일
- PPT 정돈
- 상품등록/데이터 입력
- 이미지 규격/배경제거/리사이징
- 자막 정리
- 단순 번역/교정
- 명확히 정의된 CAD 수정/도면 보조
- 반복 가능한 리서치 정리

초기 제외:

- 전략 컨설팅
- 브랜딩 전체
- 장기 개발 프로젝트
- 복잡한 건축설계
- 법률/세무/의료 등 규제 전문판단
- 결과의 주관성이 매우 높은 창작
- 실패의 비가역적 손해가 큰 작업

## 12. 가격과 완료시각을 어떻게 제시할 것인가

이 모델의 가장 어려운 문제다.

초기부터 AI가 정확한 가격과 시간을 안다고 가정하면 안 된다.

### Phase A — Assisted Quote

```text
GM 입력
→ KAPAPI가 SOW 구조화
→ 운영자/내부 공급시장으로 실행 가능성 확인
→ 가격 + 완료시각 제시
```

겉으로는 단순하지만 뒤에서는 concierge 방식으로 시작할 수 있다.

목적은 **가격·시간 예측 데이터를 얻는 것**이다.

### Phase B — Market-informed Quote

과거 거래 + 현재 가용 공급을 사용:

```text
기준원가
+ 긴급성 프리미엄
+ 실패/수정 리스크
+ KAPAPI margin
= GM 가격
```

완료시각은:

```text
현재 공급 가용성
+ 예상 작업시간
+ 검수시간
+ recovery buffer
```

으로 산정한다.

### Phase C — Near-instant Quote

반복성이 높은 카테고리에서 충분한 데이터와 공급 유동성이 확보된 경우에만 즉시 견적에 가까워진다.

따라서 **instant quote는 출발점이 아니라 증거를 쌓아 도달하는 자동화 수준**이다.

## 13. 수익 구조

사용자에게 공급자의 BID를 직접 노출하지 않는다면 KAPAPI의 수익은 단순 중개 수수료보다 **실행 가격과 조달 원가의 차이**로 설계할 수 있다.

예:

```text
GM 결제       50,000원
실행자 보상   35,000원
결제/운영비    3,000원
risk reserve   4,000원
KAPAPI margin  8,000원
```

하지만 이 구조는 동시에 KAPAPI가 다음 비용을 떠안는다는 뜻이다.

- 재작업
- 지연
- 환불
- 대체 PLAYER
- 검수
- 고객지원
- fraud/dispute

따라서 초기 핵심 지표는 거래액보다 **completed outcome contribution margin**이어야 한다.

```text
GM revenue
- executor cost
- recovery/rework cost
- payment cost
- support/QA variable cost
= contribution margin per completed task
```

## 14. 가장 큰 리스크

### 14.1 견적 오류

싼 가격과 빠른 완료시간을 약속했는데 실제 조달이 안 되면 KAPAPI가 손실을 떠안는다.

### 14.2 품질 표준화

결과를 상품화하려면 무엇이 "완료"인지 정의할 수 있어야 한다.

### 14.3 공급 유동성

즉시 실행 경험은 충분한 가용 공급이 없으면 무너진다.

### 14.4 운영비 폭증

사람이 모든 SOW, 배정, 검수, 분쟁을 처리하면 사실상 저가 외주대행사가 될 수 있다.

### 14.5 책임의 확대

중개보다 결과 책임을 더 많이 지는 구조이므로 계약·환불·하자·개인정보·저작권·전문업 규제 검토가 훨씬 중요하다.

### 14.6 직접거래보다 더 비싸질 가능성

KAPAPI가 복구/검수/risk margin을 포함하면 단순 프리랜서 직거래보다 가격이 높아질 수 있다.

따라서 고객이 지불하는 프리미엄은 **탐색·관리·실패 위험을 제거하는 가치**보다 낮아야 한다.

---

## 15. 초기 MVP

이 개선안을 검증하기 위해 거대한 자동 라우팅 엔진부터 만들지 않는다.

### GM MVP

1. 업무 설명
2. 파일 첨부
3. KAPAPI가 정리한 SOW 확인
4. 가격 + 완료예정시각 확인
5. 결제/진행
6. 진행 상태
7. 결과 다운로드
8. 승인 / 수정 요청

### PLAYER MVP

1. 스킬/작업유형 등록
2. 신원/경력 최소 검증
3. 가용시간 설정
4. 적합 TASK Offer 또는 내부 BID
5. 수락
6. 실행/제출
7. 보상

### 운영 MVP

초기에는 상당 부분 수동이어도 된다.

- SOW 확인
- 공급자 선택
- quote 결정
- 상태 감시
- QA
- recovery

중요한 것은 자동화된 척하는 것이 아니라 **사용자가 사람을 직접 찾지 않아도 실제 결과가 나오는지** 검증하는 것이다.

---

## 16. 첫 검증 실험

### 실험 A — 사용자 선택 제거

동일한 종류의 작은 업무에서:

- A: 여러 PLAYER/BID를 보여주고 GM이 선택
- B: KAPAPI가 하나의 가격/완료시각만 제시

비교:

- 의뢰 시작률
- 결제율
- 완료율
- GM이 소비한 시간
- 만족도
- 재의뢰율

### 실험 B — 결과 책임

의도적으로 운영 가능한 범위에서 지연/중도 실패 상황을 포함하여:

```text
첫 실행자 실패
→ KAPAPI가 교체
→ GM 추가 선택 없이 완료
```

측정:

- recovery success rate
- recovery cost
- 최종 납기 준수율
- GM 만족도
- margin impact

### 실험 C — 자동화 가능한 업무

사람 100% 실행과 AI/automation + human QA 구조를 비교한다.

측정:

- 원가
- 속도
- 오류율
- 수정률
- GM acceptance

---

## 17. 성공 기준과 Kill Criteria

이 개선안은 멋진 미래 그림이 아니라 **경제적으로 작동해야 하는 실행 모델**이다.

초기 검증에서 다음이 확인되어야 한다.

### Continue signals

- GM이 작업자 선택 없이 맡기는 방식을 선호한다.
- 기존 외주 탐색보다 의뢰 시간이 크게 줄어든다.
- 반복 가능한 업무에서 quote 오차가 줄어든다.
- 동일 카테고리에서 공급자가 반복적으로 확보된다.
- 실패 시 교체해도 거래 단위 경제성이 유지된다.
- GM이 관리 편의와 결과 책임에 가격 프리미엄을 지불한다.
- 재의뢰가 발생한다.

### Kill / Redesign signals

- GM이 결국 특정 PLAYER를 직접 고르기를 강하게 원한다.
- 대부분의 업무가 사전 범위 정의가 안 된다.
- 가격/시간 추정 오차가 지속적으로 크다.
- recovery 비용이 margin을 잡아먹는다.
- QA/지원 인력이 거래액에 비례하여 선형 증가한다.
- 반복 수요보다 일회성 예외 작업이 압도적이다.
- 고객이 KAPAPI 프리미엄보다 직접거래를 지속적으로 선호한다.

## 18. 핵심 데이터 플라이휠

```text
업무 요청
↓
SOW 구조
↓
quote
↓
실제 조달 PRICE × DELIVERY
↓
실행
↓
완료시간 / 수정 / 실패
↓
recovery
↓
GM acceptance
↓
더 나은 scope / quote / routing / recovery
```

장기 방어력 후보는 UI나 BID 방식이 아니라 이 데이터다.

특히 중요한 것은:

> **누가 좋은가**보다 **어떤 조건의 업무를 어떤 실행 방식으로 어떻게 끝냈는가**

이다.

## 19. 제품 진화 가설

기존 KAPAPI는 Outcome Layer를 장기 목표로 두고 Task Marketplace에서 시작한다.

이 개선안은 반대로 **Outcome UX를 초기부터 전면에 두고**, 내부 시스템의 자동화 수준을 단계적으로 높인다.

```text
Stage 0
Outcome UX + 수동 concierge execution

↓ real task/quote/execution data

Stage 1
내부 PLAYER market + structured SOW

↓ supply/liquidity/trust data

Stage 2
market-informed quote + recommendation/routing

↓ failure/recovery data

Stage 3
automatic routing + backup/recovery

↓ repeatable category automation

Stage 4
human + AI + automation orchestration

↓
Work Execution Infrastructure
```

즉 **미래의 Outcome Layer를 약속하는 Marketplace**가 아니라,

> **처음부터 Outcome처럼 보이고 작동하지만, 뒤의 실행 엔진은 수동에서 자동으로 진화하는 제품**

을 검증한다.

## 20. 현재 판단

이 개선안의 장점은 기존 KAPAPI에 기능을 더 붙이는 것이 아니라 **사용자 경험에서 마켓플레이스 요소를 덜어낸다**는 데 있다.

없애는 것:

- GM의 PLAYER 탐색
- GM의 BID 비교
- GM의 프로필 비교
- GM의 실행자 재탐색

남기는 것:

- 업무 정의
- 가격
- 완료시각
- 결과
- 수정/승인

내부로 이동하는 것:

- PRICE × DELIVERY 시장
- 실행자 선택
- 신뢰 판단
- AI/automation 선택
- 진행 감시
- recovery
- QA

따라서 이 설계의 핵심 질문은 더 이상:

> "크몽/숨고보다 매칭을 어떻게 다르게 할 것인가?"

가 아니다.

핵심 질문은:

> **"작은 디지털 업무에서 고객이 실행자를 전혀 고르지 않아도, KAPAPI가 예측 가능한 가격과 시간 안에 반복적으로 결과를 전달할 수 있는가?"**

이 질문에 실제 거래로 YES를 증명할 수 있을 때에만 이 개선안은 독립적인 사업 구조로 의미가 있다.
